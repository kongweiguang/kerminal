# 原型探索

原型是回答问题的临时代码，不是生产交付，也不能成为降低错误处理、测试或安全要求的借口。

## 选择类型

| 要回答的问题 | 类型 | 输出 |
| --- | --- | --- |
| 状态/业务规则是否成立 | logic | CLI、脚本、fixture 驱动的小程序 |
| 哪个 UI/交互方向更合适 | UI | 同一入口、同一数据的可切换变体 |
| 库、协议、构建或性能是否可行 | spike | 最小 adapter/集成与限制报告 |

细节见 [prototype-branches.md](references/prototype-branches.md)。

## 原型契约

开始前在 discovery 或当前 plan 写清：

```markdown
- 原型问题：<必须学到什么>
- 非目标：<本次不验证什么>
- 成功/失败信号：<观察到什么即可判断>
- 允许路径与数据：<隔离边界>
- 运行命令：<一条可复现命令>
- 删除/吸收条件：<何时清理或进入正式实现>
```

## 执行规则

1. 使用项目现有语言、构建工具、路由和 fixture；除非目标就是验证依赖，不引入重量级栈。
2. 在文件名、页面或入口明确标记 `PROTOTYPE`，不接入正式生产入口、持久数据和默认发布路径。
3. 默认使用临时目录、scratch 数据和沙箱；不得连接生产、真实写库或真实付费服务。
4. 暴露关键输入、状态、输出和失败原因，让用户能比较而不是只看静态截图。
5. UI 变体使用同一数据和固定 viewport；logic/spike 提供关键场景和可重复命令。
6. 只实现回答问题所需内容，不提前抽象成正式框架。

执行位置由 Codex 决定。与当前 checkout 改动无关、需要比较多个实现或会污染正式入口时优先原生 worktree；Updeng 不创建第二套原型分支命令。

## 收口

- 采用：把结论写入 plan/tech decision，删除原型或吸收到正式实现，去掉标记并补生产测试。
- 拒绝：删除原型，在 discovery 记录不可行证据和拒绝原因，避免重复探索。
- 未决：保留最小原型、负责人和过期条件，不把它写入 business 文档。

正式实现必须重新满足领域 Skill、测试、文档、恢复和真实运行门禁；原型成功不是发布证据。
