# 通用诊断

## 核心纪律

1. 没有反馈回路，不进入修复。
2. 先确认复现的是用户报告的症状，不修旁边另一个问题。
3. 一次只验证一个可证伪假设，保留第一条因果错误。
4. 性能问题先建立基线，偶发问题记录复现率和环境。
5. 临时插桩必须可定位、可删除、不泄漏敏感数据。
6. 修复后保留回归测试或明确说明测试缝隙。

## 诊断流程

### 1. 建立反馈回路

优先使用能穿过真实问题路径的最窄稳定入口：自动化失败测试、命令/HTTP/日志回放、浏览器或桌面自动化、最小 harness、压力循环，最后才是人工协助。

记录命令或入口、期望、实际症状、环境、稳定性/失败率和证据位置。构造细节见 [feedback-loops.md](references/feedback-loops.md)。

### 2. 复现并收窄

- 固定版本、配置、数据、时区、seed、并发、缓存和网络条件。
- 逐步减少输入、依赖与系统范围，比较正常/异常环境。
- 无法复现时列出已尝试回路和缺口，再请求必要日志、fixture、HAR、截图、硬件或环境访问。

### 3. 排序假设

修改前列出 3 到 5 个可证伪假设：

```markdown
| 排名 | 假设 | 如果为真应观察到 | 验证方式 |
| --- | --- | --- | --- |
| 1 | <原因> | <预测> | <命令、probe 或对比> |
```

用最便宜且区分度最高的 probe 验证，不同时改变多个变量。

### 4. 定点验证

优先调试器、断言、query plan、profile、trace 和现有日志；需要临时日志时使用唯一前缀，例如 `[DEBUG-UPDENG-<短码>]`，只记录区分假设所需状态。

涉及跨层问题时按 UI -> wrapper -> API/IPC -> service -> storage/plugin/OS 逐层缩小，不因某一层测试通过就假设整条链路正确。

### 5. 修复与回归

- 把最小复现转为行为回归测试或可重复验证脚本。
- 修复只覆盖已证实根因，不顺手重构扩大变量。
- 运行最小回归、原始反馈回路、相邻测试和受影响真实路径。
- 失败、取消、重试、恢复和资源清理属于同一修复验收。

### 6. 清理与记录

删除临时日志、harness、fixture 和开关，或把必要工具移入明确诊断目录。记录根因、修复点、验证命令、复现率变化和未覆盖风险；将重复故障模式交给 `updeng-project-skill-maintenance` 人工沉淀。

## 停止条件

- 无法建立有效反馈回路，且缺少必须由用户或环境提供的证据。
- 操作需要生产、真实数据、凭据或远程写入，但没有授权与恢复方案。
- 诊断发现目标/业务语义本身不一致，应回到 requirement/domain/plan 收敛。
- 同一假设连续验证无新证据，或连续多轮无实质进展，应记录 blocker，而不是继续盲试。
