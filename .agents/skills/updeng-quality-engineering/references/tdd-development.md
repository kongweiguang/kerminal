# 测试先行开发

## 测试原则

1. 测用户或调用方可观察行为，不测内部调用顺序。
2. 优先公开 API、CLI、UI、领域接口、IPC 或稳定模块边界。
3. 一次写一个正确失败的测试，再写刚好通过的实现。
4. 只在绿色状态重构；红色状态不夹带架构整理。
5. 测试必须能因目标缺陷失败，不能只证明 mock 自己。

测试层级、mock 边界和命名见 [test-design.md](references/test-design.md)。

## 工作流

### 1. 选择测试缝隙

先读取最近似测试、fixture、测试命令和真实调用入口。明确用户可观察行为、最高且稳定的测试层、必须覆盖的失败路径，以及无法自动化的人工证据。

不要为了写测试暴露私有实现；如果没有稳定缝隙，把它记录为架构风险。

### 2. 拆纵向切片

每个切片贯通完成该行为所需的最少层，不按“先数据、再接口、再页面”横向堆半成品：

```markdown
| 顺序 | 行为 | 入口 | 期望 | 验证 |
| --- | --- | --- | --- | --- |
| 1 | <最小完整行为> | <公开入口> | <可观察结果> | <命令> |
```

### 3. 红绿循环

1. **RED**：运行新增测试，确认它因目标行为缺失或缺陷而失败，而非语法、fixture 或环境错误。
2. **GREEN**：实现让当前行为通过的最小生产代码。
3. **BROADEN**：运行相邻测试与受影响集成入口，防止局部绿色掩盖回归。
4. **REFACTOR**：全部相关测试绿色后再消除真实重复、深化边界或整理名称。
5. **EVIDENCE**：把命令和结果写入 `tasks.json.verification`；工具执行历史进入 `operations.jsonl`。

禁止批量写一组幻想测试后再倒推实现，也禁止为 fixture 硬编码生产分支。

### 4. 收口

- 记录新增/修改的行为测试、RED 失败原因和最终通过证据。
- 说明未自动化行为及人工验证。
- 清理临时 fixture、日志和测试开关。
- 发现测试只能依赖私有细节时，使用架构深化评估稳定接口，而不是永久扩大 mock。

## 与其它能力协作

- 缺陷先使用 `updeng-quality-engineering` 的 diagnosis reference 建立正确复现，再将复现固化为回归测试。
- UI/桌面测试结合对应领域 Skill 的真实运行和截图门禁。
- 数据、发布或远程高风险测试先确认隔离、备份、恢复和授权。
- `tasks.json` 中的测试检查必须与验收一一对应；测试通过不自动完成文档、评审或真实环境门禁。
