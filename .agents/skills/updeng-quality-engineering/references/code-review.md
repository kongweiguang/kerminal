# 实现评审

## 评审姿态

问题优先，不写泛泛表扬。评审不是只看 diff 的格式检查，而是对照需求、计划、业务事实、调用链和验证证据判断实现是否正确。

## 工作流程

1. 查看 `git status --short`、diff stat 和变更文件，区分本任务改动与既有未归因改动。
2. 读取需求、当前 plan/task、验收、业务/集成文档和最相近实现。
3. 沿调用方、公共契约、状态/数据流和失败路径阅读受影响代码，不只看补丁片段。
4. 先检查需求符合性和范围，再检查正确性、安全、事务、权限、并发、资源、兼容、性能和可维护性。
5. 检查验证是否穿过真实风险边界；能运行聚焦检查时实际运行。
6. 对 UI/桌面行为核对真实运行和截图，对发布/迁移核对恢复与产物证据。
7. 按严重程度输出带文件和行号的发现；没有发现时明确说明剩余风险和未运行检查。

## 严重级别

- `P0`：数据丢失、安全漏洞、不可恢复破坏、无法构建或核心流程完全不可用。
- `P1`：高概率用户可见回归、权限/业务结果错误、发布阻断或重大兼容问题。
- `P2`：重要边界缺陷、恢复/校验缺失、明显竞态或较快会造成事故的维护风险。
- `P3`：低风险改进；没有实际影响时不要凑数。

格式：

```markdown
- [P1] <短标题> - <file>:<line>
  <触发条件、实际影响、证据和最小修复方向>
```

## 检查重点

- 每个验收点都有实现、验证或明确非目标，未用“后续再补”掩盖缺口。
- 公开 API、配置、序列化、数据库和 UI 行为与调用方保持兼容，变更有迁移口径。
- 外部输入、路径、ID、URL、分页、空值、权限和错误码在权威边界校验。
- 事务、缓存、事件、重试、幂等、取消、资源清理和并发所有权明确。
- 测试验证行为而非 mock 自己，覆盖最高风险失败路径和回归模式。
- diff 没有无关重构、调试残留、secret、宽权限或未说明的生成文件。
- business/integrations 只描述已落地事实，discovery 没被误写成现状。
- worktree/subagent 输出已由 controller 合并，并在目标 checkout 重新验证。

## 收口

只读评审不修改文件。用户要求“评审并修复”时，先给出发现，再把修复绑定到当前 plan/task、owned paths 和验证，不让 reviewer 与实现者并发写同一路径。
