# 行为测试设计

## 好测试

- 从 API、CLI、UI、IPC 或领域公开接口验证可观察行为。
- 测试名使用领域语言，描述 actor、行为和条件。
- 断言结果、状态变化、错误模式和副作用。
- 尽量穿过真实协作路径，只替换不可控边界。
- 对缺陷测试先确认它在修复前因正确原因失败。

## 坏测试

- 直接测试私有 helper、内部调用顺序或无业务意义的结构。
- 大量 mock 当前仓库内部模块，行为坏了仍通过。
- 只断言快照/类型形状，不验证结果和副作用。
- 用固定 sleep、超长 timeout 或重试掩盖竞态。
- 为测试 fixture 在生产代码加入专用分支。

## Mock 边界

适合替换：外部网络、时钟、随机数、付费服务、危险文件/生产写入和不可稳定控制的系统边界。

避免替换：当前仓库内部业务协作、权限判断、事务、序列化、路径校验、缓存失效和真正风险点。

## 选择层级

| 层级 | 适用行为 |
| --- | --- |
| 单元 | 纯算法、policy、parser、状态机 |
| 集成 | 服务、数据库、权限、序列化、事务、插件 |
| API/CLI/IPC | 稳定调用边界和错误契约 |
| E2E/UI/桌面 | 关键用户流程、真实运行时和平台行为 |

选择能准确覆盖风险的最窄稳定入口。过低会耦合实现，过高会慢且难定位；高风险链路通常需要分层组合而不是只选一种。
