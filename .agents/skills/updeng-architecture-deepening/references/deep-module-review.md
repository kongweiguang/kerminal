# 深模块评估

## 评估维度

| 维度 | 核心问题 |
| --- | --- |
| 接口复杂度 | 调用方需要知道多少顺序、配置、错误和不变量 |
| 实现深度 | 模块是否隐藏并承担足够行为，而非转发 |
| 局部性 | 规则、修改和缺陷是否集中 |
| 杠杆 | 调用方通过少量接口获得多少稳定能力 |
| 测试缝隙 | 能否从接口验证真实行为与失败 |
| 适配需求 | 是否有真实替换、平台或测试边界 |

## 常见浅模块

- 只改名不隐藏复杂度的 wrapper。
- 每个方法一行转调的 service。
- 只为测试抽出的函数，但调用方仍重复不变量。
- 聚合无关函数的 `utils`。
- 只搬运 props、状态和副作用仍散在父级的组件。
- 只有一个实现且没有替换压力的抽象工厂。

## 深化方式

- 把权限、事务、缓存、错误和序列化不变量推到接口背后。
- 用领域概念命名模块，提供高层行为而不是技术步骤。
- 外部系统放在 adapter 后，业务依赖稳定 port/policy。
- 让状态和副作用有单一 owner，缩小调用方组合负担。
- 保持接口小而完整，避免暴露内部生命周期顺序。

## 渐进顺序

1. 锁定当前行为和失败测试。
2. 引入新边界并迁移一个真实调用方。
3. 验证行为、性能和可观测性。
4. 逐步迁移其余调用方。
5. 删除旧入口和重复逻辑。
6. 在目标 checkout 运行合并后验证与文档核对。
