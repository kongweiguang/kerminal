# 架构深化评估

## 目标

提高局部性、接口杠杆、可测试性、替换能力和 AI 可导航性。架构报告只是决策输入，具体实施仍使用生产计划和领域 Skill。

## 先读事实

- 领域词汇、已实现业务文档、相关技术决策和当前 plan。
- 最近似实现、调用链、失败模式、测试和用户指出的实际摩擦。
- 有 `.codegraph/` 时优先使用 CodeGraph 查看符号、调用者和跨文件路径。

不要基于文件名或通用偏好提抽象。

## 发现候选

重点寻找：

- 一个业务概念散在多个薄文件，调用方重复权限、事务、错误或数据形状。
- 模块接口与实现同样复杂，只增加转发层。
- 测试只能碰私有细节，真实协作缺乏稳定入口。
- 新能力总要同步修改一串无清晰 owner 的文件。
- 业务直接依赖数据库、SDK、平台 API、UI runtime 或具体存储，替换和测试困难。
- 生产文件持续接近/超过项目规模门槛，测试 fixture/helper 混入源码。

对每个候选做“删除测试”：删除后复杂度若消失，它可能是多余间接层；若复杂度分散回多个调用方，它正在提供局部性。

评估维度见 [deep-module-review.md](references/deep-module-review.md)。

## 输出评估

每个候选说明文件/符号、当前摩擦证据、建议边界、局部性与杠杆收益、测试改善、SOLID/模式理由、迁移风险、回滚和推荐强度。需要统一格式时使用 [report-template.md](references/report-template.md)。

推荐强度只使用：`Strong`、`Worth exploring`、`Speculative`。没有真实摩擦的候选应删除。

## 定案与迁移

用户选择方向后：

1. 定义新模块承担的概念、最小接口、不变量、错误和副作用。
2. 识别真实 adapter 数量；只有一个假想实现时警惕过早抽象。
3. 先用行为测试锁定当前契约。
4. 引入新接口，迁移一个调用方作为 tracer bullet，但计划必须覆盖完整生产迁移。
5. 按依赖和 owned/shared paths 拆 child plan/task；独立切片可由原生 subagent/worktree 执行，共享契约由 controller 串行集成。
6. 逐步迁移、合并后验证，再删除旧入口和重复逻辑。

重大长期取舍使用 `updeng-product-planning` 的技术决策流程；架构阻塞或不可逆选择写入 `blockers.json`。

## 禁止事项

- 不为“套 SOLID/模式”扩大范围。
- 不拆分已经足够深、稳定且局部的模块。
- 不在行为未锁定时重写核心路径。
- 不把 wrapper、utils 或每方法一行的 service 当深模块。
- 不把测试 fixture、mock、原型或临时 adapter 放进生产源码。
- 不用 MVP/tracer bullet 逃避完整错误、权限、迁移、回滚和文档路径。
